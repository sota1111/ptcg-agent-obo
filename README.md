# Pokémon TCG AI Battle Challenge 攻略戦略

このリポジトリは、攻略戦略だけでなく、戦略を検証する対戦・評価基盤、実験成果、
対戦ログ再生、ブラウザ/ネイティブ iOS ビューアをまとめたプロジェクト成果物です。

## セットアップと検証

```bash
npm install
npm run lint
npm run typecheck
npm test
```

対戦ログのターミナルビューアは次のように起動できます。

```bash
npm run viewer -- src/__tests__/fixtures/battle-log.real-anonymized.json
```

主要ディレクトリ:

- `src/` — 対戦、評価、分析、ログ再生とビューア
- `artifacts/` — 再現可能な評価結果とレポート
- `docs/` — 各機能の設計・運用手順
- `config/` — 評価プロファイル
- `ios/PTCGBattleViewer/` — ネイティブ iOS 盤面ビューア

Kaggle の [PTCG AI Battle Challenge Simulation](https://www.kaggle.com/competitions/pokemon-tcg-ai-battle) で、安定して勝率を高めるための設計・探索・検証戦略です。

## 結論

最も勝ち筋が太いのは、1つの高速・安定デッキに絞り、ルールベースで合法手と定石を保証したうえで、非公開情報を複数の「あり得る世界」にサンプリングし、公式 `search_*` API で先読みするハイブリッドエージェントです。

優先順位は次の通りです。

1. 提出形式・合法手・制限時間を絶対に落とさない Safety layer
2. デッキと方策を同時評価できる再現可能なローカル対戦基盤
3. 盤面価値関数を使う決定論的探索
4. 複数の非公開情報仮説を使う determinization
5. 対戦分布への適応とアンサンブル
6. ログ蓄積後に模倣学習・強化学習を探索 prior / value へ追加

## 公式仕様から導ける設計条件

- 提出物は `agent(obs_dict) -> list[int]` を持つ `main.py` と60枚の `deck.csv`。
- 観測には過去イベント、現在盤面、合法な選択肢が含まれる。
- 自分の手札は見える一方、相手手札は枚数のみ、サイドは裏向きで、部分観測ゲームである。
- 行動は合法な選択肢のインデックス列。対象、枚数、Yes/No、進化先など連続選択も扱う必要がある。
- 公式 API には仮想状態を作る `search_begin`、分岐を進める `search_step`、解放する `search_end` / `search_release` がある。
- 勝敗にはサイド、場のポケモン、山札切れなど複数の条件があるため、単純なダメージ最大化では足りない。

## 認証済み Kaggle Rules の確認結果

2026-07-24 に、参加承諾済みアカウントで Kaggle CLI から Competition の Rules、
Evaluation、Timeline、Submission、FAQ を取得し、`ptcg-agent-core` の
`docs/kaggle-submission.md` と照合しました。戦略と運用に影響する最新条件は次の通りです。

- 1チームは最大5人、1日最大5提出、最終審査に選べる提出は最大2件。
- 新規参加・チーム統合期限は **2026-08-09 23:59 UTC**、最終提出期限は
  **2026-08-16 23:59 UTC**。その後、概ね2026-08-31まで対戦を継続して最終順位を確定する。
- 提出物はトップレベルに `main.py` と `deck.csv` を含む `.tar.gz`。ファイルは
  `/kaggle_simulations/agent/` に配置されるため、import と相対パスはこの実行位置に対応させる。
- 各提出は最初に自分自身との Validation Episode を行う。成功時は
  `μ0=600` でマッチングプールに入り、近い rating の相手と継続的に対戦する。
- rating は勝敗・引き分けで更新され、勝ち方の点差は更新量に影響しない。新しい提出ほど
  対戦頻度が高く、Leaderboard にはチーム内最高スコアの agent だけが表示される。
- Simulation competition に Private Leaderboard はなく、episode replay と行動は公開・
  ダウンロード可能になる場合がある。秘密の戦略を replay から隠せる前提を置かない。
- episode 評価中は Submission / Environment の外から情報を取得したり、外へ送信したり
  できない。対戦中の外部 API・LLM・ネットワーク呼び出しは禁止前提とする。
- Competition Data は本コンペへの参加目的に限定し、非参加者への再配布は禁止。
  コンペ終了後は速やかに削除する。外部データ・モデルは、全参加者が無償または合理的な
  費用で利用でき、必要な権利を確保したものに限る。
- 優勝 Submission は MIT を含む OSI 承認ライセンスでのソース提供と、再現可能な詳細説明を
  求められる。提出 commit、deck hash、依存関係、実験条件を今から追跡する。

Kaggle の FAQ は提出サイズ、HDD、RAM、vCPU を動的変数で表示しており、認証済み CLI の
取得結果でも具体値へ展開されませんでした。これらの数値は推測せず、提出直前にブラウザの
表示または実ジョブで再確認します。したがって Safety layer は固定上限ぎりぎりではなく、
時間・メモリ・アーカイブ容量に余裕を持たせます。

## 推奨アーキテクチャ

### 1. Safety layer

`select.type/context` ごとに選択を処理し、常に選択数、重複禁止、インデックス範囲を満たします。未対応コンテキスト、例外、探索予算切れでは、次の決定論的フォールバックを使います。

1. 即勝利
2. 即敗北の回避
3. 有効な攻撃
4. 展開・エネルギー・進化
5. ターン終了を含む最初の合法手

無効行動、例外、メモリリーク、時間切れをゼロにします。探索状態は `search_release` と `search_end` で必ず解放します。

### 2. Belief state

既知の60枚デッキから、場・トラッシュ・公開ログに現れたカードを差し引き、未知カード集合を保持します。相手デッキは候補アーキタイプの混合分布とし、公開カードごとに更新します。

未知の相手手札・山札順・サイドを制約付きで `K` 通りサンプルし、各世界を `search_begin` に渡します。行動評価は平均値だけでなく分散も考慮します。

```text
score(a) = mean(V(a, world_k)) - λ * std(V(a, world_k))
```

初期は `λ > 0` とし、一部の都合のよい仮説だけで強い手より、多くの構成に崩れにくい手を選びます。

### 3. 探索

初期版は深さ制限付き expectimax / best-response 探索とします。自分の手番では最大化、相手手番では相手価値を最大化し、コイントス等は期待値を取ります。

- 同値な行動順を正規化
- 攻撃・進化・サーチ・エネルギー付与を優先
- 定石スコア上位 `B` 手に枝刈り
- 公開盤面、手札、残りデッキ多重集合、ターン制約をキーにキャッシュ
- 意思決定ごとの deadline と反復深化

速度に余裕が出たら Information Set MCTS を試します。重要なのは探索方式の名前ではなく、公式エンジン上で正確に遷移し、時間内に必ず合法手を返すことです。

### 4. 盤面価値関数

終局は勝ち `+1`、負け `-1`。非終局では次を正規化して重み付けします。

- サイド差と次のサイド獲得までの攻撃回数
- 相手 Active を倒せる確率 / 自分 Active が倒される確率
- 攻撃可能になるまでのテンポとエネルギー効率
- 手札の選択肢、ドロー／サーチ可能性、山札切れ余裕
- 展開済みアタッカー数と次アタッカーの準備度
- 逃げコスト、特殊状態、ベンチ枠、スタジアム
- 複数サイドを取られるポケモンのリスクとサイドレース

序盤・中盤・終盤で係数を切り替え、終盤はヒューリスティックより勝敗までの手数を優先します。

## デッキ戦略

### 現時点の推奨: 水単「Mega Abomasnow ex」

メインタイプは **水** を推奨します。現時点の第一候補は、Mega Abomasnow ex を主力にした次の60枚です。
マリィのオーロンゲex候補との100試合比較と候補リストは
[`docs/deck-comparison-sot-2128.md`](docs/deck-comparison-sot-2128.md) に記録しています。

| 枚数 | カード | 役割 |
| ---: | --- | --- |
| 35 | Basic Water Energy | 攻撃・Mega Abomasnow ex の `Hammer-lanche` の打点源 |
| 4 | Snover | Mega Abomasnow ex の進化元 |
| 4 | Mega Abomasnow ex | 350 HP の主力アタッカー |
| 2 | Kyogre | たねの副アタッカー兼、序盤の受け |
| 4 | Mega Signal | 主力へのアクセス |
| 1 | Maximum Belt | ACE SPEC。対exの打点補助 |
| 2 | Cyrano | 盤面展開 |
| 4 | Lillie's Determination | 手札更新 |
| 4 | Waitress | ドロー |
| **60** | **合計** | |

`deck.csv` のカードID順では次の構成です。

```text
3×35, 721×2, 722×4, 723×4, 1145×4, 1158×1,
1205×2, 1227×4, 1235×4
```

水単を推す理由は、単にタイプ相性ではなく、次の3点です。

1. **方策が単純でAIが扱いやすい。** Snoverを置き、Mega Abomasnow exへ進化し、水エネルギーを集めて攻撃する主線が明確です。
2. **高耐久と高い再現性を両立する。** 350 HPの主力、厚いエネルギー、サーチ4枚、ドロー8枚で、複雑な多色コンボより事故と探索分岐を抑えられます。
3. **実測で暫定首位。** 同一greedy方策で26候補を比較したローカル評価では、25,800試合・fault 0。confirm段階でこの構成は勝率81.65%（3,112決着、Wilson 95% CI 80.25–82.97%）で、2位のCrustle構成（76.46%、CI 74.94–77.92%）と信頼区間が分離しました。

ただし、これは **現在のローカル評価系における最良の初期値** であり、大会全体に対する絶対最適の証明ではありません。greedy方策での比較なので、提出用探索エージェントとの相互作用や本番上位メタで順位が変わる可能性があります。特に、たねポケモンが6枚しかなく盤面全滅リスクがある点と、35エネルギーゆえに手札の選択肢が細くなる点は継続監視します。

### 更新方法

この60枚を固定したまま方策を改善し、その後にデッキを再比較します。

- 初動成功率が高い
- 1〜2ターン先の計画が明確
- サーチとドローが多い
- 単一コンボに依存しない
- 主要アーキタイプへの極端な不利が少ない
- 先攻・後攻の差が小さい

評価は全組合せ・両席・複数 seed で行い、Wilson 信頼区間付きのベースラインを作ります。その後、カード枚数を1要素ずつ変える局所探索、遺伝的探索、Bayesian optimization の順で60枚を最適化します。新構成への切り替えは、同一方策・独立seed・両席のconfirm評価で信頼区間が現構成を上回った場合だけ行います。

## 実験ロードマップ

### Phase 0 — 正しさ（1日）

- 公式サンプルを提出可能な形で再現
- 全 `SelectType/SelectContext` をログ化
- 例外率、無効行動率、時間超過率をゼロにする
- seed、両席、デッキ、agent version を保存

### Phase 1 — ルールベース（2〜3日）

- 即勝利、敗北回避、攻撃、展開、進化、エネルギー、撤退の規則
- サンプル4デッキ総当たりを各席・複数 seed で200〜500試合
- paired seed と信頼区間で変更前後を比較

### Phase 2 — 探索（3〜5日）

- `search_*` による1〜2 ply
- deadline、反復深化、キャッシュ、枝刈り
- 探索なし、完全情報1仮説、複数仮説の ablation

### Phase 3 — メタ適応（継続）

- 相手アーキタイプ別勝率を更新
- 上位・頻出メタを重み付けした相手プールで評価
- 主力と、その天敵を狙う候補を保持
- リーダーボードの短期変動だけでは提出を変えない

### Phase 4 — 学習（余力）

- 探索結果の `(state, visit distribution, outcome)` を保存
- 小型 policy/value model を探索 prior と leaf value に使う
- 対戦中の生 LLM 呼び出しには依存しない
- 未知カードではルールベースへ安全にフォールバック

## 昇格基準

提出候補は固定評価スイートで次をすべて満たした場合だけ採用します。

- 10,000試合規模でベースラインより有意に高い（95% CI で50%超）
- 主要マッチアップで致命的な崩壊がない
- 先攻・後攻の両方で改善または非劣性
- 無効行動・例外・時間切れがゼロ
- 意思決定時間 p99 に十分な余裕がある
- 同じ seed と version で再現できる
